  ❌ Breaks Chaos SeqCst/SWeMR lockfree guarantee
  ❌ Causes subtle data races and 3-10× latency spikes on contention

┌─────────────────┬──────────────┬─────────────────────────────────┐
│ Operation       │ Recommended  │ When / Why                      │
├─────────────────┼──────────────┼─────────────────────────────────┤

│ store()         │ Release      │ Publishing data to other thread │

  • ASSUM: #ASSUME_CORRECT_ORDERING verified via compile-time lint
  • B32: Performance gains (5-20%) only with proper synchronization

WHY EACH ORDERING:
  Acquire (load):
    - Prevents subsequent code from reordering before load
    - Sees all writes that happened-before this Acquire
    - Critical for reading shared state (config, flags, etc)

When Relaxed is ACCEPTABLE (with documentation):
  ✓ Non-coordinating counters: metrics, statistics, performance tracking

  ❌ State coordination (flags, config, state machine)
  ❌ Handoff of data between threads
  ❌ Lock-free data structures (queues, stacks, hash tables)
  ❌ Publishing results from computation

To allow Relaxed (with caution):

## Operation-Specific Examples

### Example 1: Load Operation (Acquire)

**Bad Code:**
```rust
#[derive(ComputationalCapsule)]
#[capsule(size = "64B", tier = "T1")]
struct ConfigCapsule {
    enabled: AtomicBool,
}

impl ConfigCapsule {
    fn is_enabled(&self) -> bool {
        self.enabled.load(Ordering::Relaxed)  // ❌ BAD
    }
}
```

**Error Message:**
```
FIX FOR THIS CODE:
  state.load(Ordering::Acquire)  // See updates from other threads

WHY EACH ORDERING:
  Acquire (load):
    - Prevents subsequent code from reordering before load
    - Sees all writes that happened-before this Acquire
    - Critical for reading shared state (config, flags, etc)

PERFORMANCE IMPACT:
  5-15% improvement: Acquire synchronizes reads without full cost of SeqCst
```

**Fixed Code:**
```rust
impl ConfigCapsule {
    fn is_enabled(&self) -> bool {
        self.enabled.load(Ordering::Acquire)  // ✓ GOOD
    }
}
```

### Example 2: Store Operation (Release)

**Bad Code:**
```rust
impl ConfigCapsule {
    fn set_enabled(&self, value: bool) {
        self.enabled.store(value, Ordering::Relaxed);  // ❌ BAD
    }
}
```

**Error Message:**
```
FIX FOR THIS CODE:
  state.store(42, Ordering::Release)  // Publish to other threads

WHY EACH ORDERING:
  Release (store):
    - Prevents preceding code from reordering after store
    - Ensures all writes before this Release are visible
    - Critical for publishing data to other threads

PERFORMANCE IMPACT:
  5-20% improvement: Release publishes without sequentially consistent cost
```

**Fixed Code:**
```rust
impl ConfigCapsule {
    fn set_enabled(&self, value: bool) {
        self.enabled.store(value, Ordering::Release);  // ✓ GOOD
    }
}
```

### Example 3: CompareExchange (SeqCst)

**Bad Code:**
```rust
#[derive(ComputationalCapsule)]
#[capsule(size = "64B", tier = "T1")]
struct LockfreeCapsule {
    state: AtomicU64,
}

impl LockfreeCapsule {
    fn try_lock(&self, old: u64, new: u64) -> Result<u64, u64> {
        self.state.compare_exchange(
            old,
            new,
            Ordering::Relaxed,  // ❌ BAD
            Ordering::Relaxed,  // ❌ BAD
        )
    }
}
```

**Error Message:**
```
FIX FOR THIS CODE:
  state.compare_exchange(old, new, Ordering::SeqCst, Ordering::SeqCst)

WHY EACH ORDERING:
  SeqCst (compare_exchange):
    - Enforces global ordering across all threads
    - Creates synchronization point (like acquiring lock)
    - Necessary for lock-free algorithms (queues, stacks)

FRAMEWORK COMPLIANCE:
  This is critical for lockfree correctness per Chaos mandate
```

**Fixed Code:**
```rust
impl LockfreeCapsule {
    fn try_lock(&self, old: u64, new: u64) -> Result<u64, u64> {
        self.state.compare_exchange(
            old,
            new,
            Ordering::SeqCst,  // ✓ GOOD
            Ordering::SeqCst,  // ✓ GOOD
        )
    }
}
```

### Example 4: Acceptable Relaxed (Metrics Counter)

**Suppressed Code (with documentation):**
```rust
#[derive(ComputationalCapsule)]
#[capsule(size = "64B", tier = "T0")]
struct MetricsCapsule {
    request_count: AtomicU64,
}

impl MetricsCapsule {
    #[allow(clippy::capsule_memory_ordering)]
    fn increment_requests(&self) {
        // SAFE: This counter doesn't coordinate behavior. Relaxed is acceptable
        // because we only read it asynchronously for metrics, never for control.
        // Performance benefit: ~5-10ns faster per increment (no sync overhead).
        self.request_count.fetch_add(1, Ordering::Relaxed);  // ✓ OK with suppression
    }

    fn get_request_count(&self) -> u64 {
        // Note: Possible stale read (acceptable for metrics)
        self.request_count.load(Ordering::Relaxed)
    }
}
```

## Memory Ordering Decision Tree

```
Question: What operation am I performing?

├─ load()
│  └─ Do I need to see other thread's writes? YES
│     └─ Use: Ordering::Acquire (5-15% faster than SeqCst)
│
├─ store()
│  └─ Do I need other threads to see my writes? YES
│     └─ Use: Ordering::Release (5-20% faster than SeqCst)
│
├─ swap() / fetch_add() / fetch_or() / etc
│  └─ Do I need both read and write sync? YES
│     └─ Single global order needed? (rare)
│        ├─ NO → Use: Ordering::AcqRel (best performance)
│        └─ YES → Use: Ordering::SeqCst (full ordering)
│
└─ Is this a non-coordinating counter (metrics only)?
   ├─ YES → Relaxed acceptable (with documentation + suppress)
   └─ NO  → Use proper ordering for your operation type
```

## Framework Integration

### UCE34 Q10 (Tier Selection Context)

The memory ordering lint validates **Q10a (Capsule Foundation)** requirements:
- **Q10a Checkpoint**: Atomic operations use correct memory ordering
- **Q10b (Analyze)**: Amdahl's Law shows 5-20% gains from correct ordering
- **Q10c (Choose Tier)**: Tier selection assumes correct memory ordering

### Chaos Mandate

The Chaos (Computational Capsule) mandate requires:
- 100% lockfree design (no mutex/RwLock)
- Correct memory ordering for synchronization
- Verification via compile-time lint (this lint)
- No scattered atomics with inconsistent ordering

### ASSUM Framework

Every memory ordering decision is captured as:
```
#ASSUME_CORRECT_ORDERING: Relaxed not used for coordination
#VERIFY_CORRECT_ORDERING: Lint detects violations automatically
```

### B32 Framework

Performance improvements with correct ordering:
- Baseline: Relaxed (no synchronization)
- Acquire/Release: 5-20% improvement (less CPU overhead than SeqCst)
- SeqCst: Full ordering (may have higher overhead)
- Measurement: 95% CI, 1000+ iterations per B32 standards
