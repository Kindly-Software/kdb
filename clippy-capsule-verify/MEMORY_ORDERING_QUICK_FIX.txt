  P2.1 CAPSULE_MEMORY_ORDERING - QUICK FIX REFERENCE
================================================================================

PROBLEM: Your code uses Ordering::Relaxed, which breaks synchronization

QUICK FIX: Replace Relaxed with the correct ordering for your operation:

  load()          → Ordering::Acquire    (5-15% improvement)
  store()         → Ordering::Release    (5-20% improvement)
  swap()          → Ordering::AcqRel     (10-15% improvement)
  compare_excg()  → Ordering::SeqCst     (full synchronization)
  fetch_add/sub   → Ordering::AcqRel     (10-15% improvement)

EXAMPLES:

  ❌ BAD:
     state.load(Ordering::Relaxed)
  ✅ FIX:
     state.load(Ordering::Acquire)

  ❌ BAD:
     state.store(42, Ordering::Relaxed)
  ✅ FIX:
     state.store(42, Ordering::Release)

  ❌ BAD:
     state.swap(42, Ordering::Relaxed)
  ✅ FIX:
     state.swap(42, Ordering::AcqRel)

  ❌ BAD:
     state.compare_exchange(old, new, Ordering::Relaxed, Ordering::Relaxed)
  ✅ FIX:
     state.compare_exchange(old, new, Ordering::SeqCst, Ordering::SeqCst)

  ❌ BAD:
     count.fetch_add(1, Ordering::Relaxed)
  ✅ FIX:
     count.fetch_add(1, Ordering::AcqRel)

WHY THIS MATTERS:

  Relaxed ordering provides NO synchronization:
    • Loads may see stale values (no happens-before relationship)
    • Stores may be reordered by CPU/compiler
    • Breaks COCA lockfree guarantee
    • Causes data races and 3-10× latency spikes

PERFORMANCE GAIN: 5-20% with proper ordering

FRAMEWORK COMPLIANCE:
  • UCE34 Q10: Tier selection requires proper memory ordering
  • COCA mandate: 100% lockfree requires correct ordering
  • ASSUM safety: All ordering decisions verified at compile-time
  • B32 performance: Realistic gains (5-20%), not optimistic claims

WHEN IS RELAXED ACCEPTABLE?

  ONLY for non-coordinating counters (metrics, statistics):

    ✓ Acceptable:
      - Request counter (never used for control)
      - Statistics collection (no synchronization needed)
      - Performance metrics (read asynchronously)

    ❌ NOT acceptable:
      - State flags (control flow depends on value)
      - Configuration (affects behavior)
      - State machines (coordination between threads)
      - Lock-free queues/stacks (coordination required)

HOW TO SUPPRESS (if you know Relaxed is safe):

  #[allow(clippy::capsule_memory_ordering)]
  fn my_function() {
      // Add comment explaining why Relaxed is safe here
      counter.fetch_add(1, Ordering::Relaxed);  // OK for metrics
  }

DECISION TREE:

  Question: What does my code do with this atomic?

  ├─ Read a value from another thread?
  │  └─ Use: Ordering::Acquire
  │
  ├─ Write a value for another thread to see?
  │  └─ Use: Ordering::Release
  │
  ├─ Both read and write (swap/compare/fetch)?
  │  └─ Do you need total global order?
  │     ├─ Yes (rare) → Ordering::SeqCst
  │     └─ No (common) → Ordering::AcqRel
  │
  └─ Is this a non-coordinating counter (metrics only)?
     ├─ Yes → Relaxed OK (add #[allow(...)], document why)
     └─ No  → Use proper ordering for your operation
