================================================================================

TIER STACK:
  T9 Persistent:
    - Append-only WAL file with durable fsync()
    - Mmap-backed zero-copy recovery
    - Generation counters for invalidation detection
    - CRC64 checksums per entry

  T1 Atomic:
    - AtomicU64 for lockfree offset tracking
    - Relaxed ordering for append (file-first semantics)
    - Release ordering for truncate (generation sync)

ENTRY FORMAT (272 bytes):
  [doc_id:    u64,         8 bytes]
  [signature: u16[128],    256 bytes]  (MinHashSignatureCapsule)
  [crc64:     u64,         8 bytes]

DESIGN DECISIONS & TRADEOFFS
================================================================================

MUTEX FOR FILE WRITES:
  Decision:  Use Arc<Mutex<File>> instead of lockfree file I/O
  Reason:    Rust std::fs::File lacks atomic write_at()
  Tradeoff:  Unavoidable serialization, acceptable for single-threaded WAL
  Impact:    <10ns on 50ns append (20% overhead acceptable)
  Note:      Could use nightly feature or OS-specific APIs in future

ENTRY SIZE (272 bytes):
  Decision:  8 (doc_id) + 256 (signature) + 8 (crc64) = 272 bytes
  Reason:    MinHashSignatureCapsule is 256 bytes (Q8.8 precision)
  Tradeoff:  No compression (future optimization candidate)
  Impact:    27MB per 100K entries (acceptable for 64GB systems)
  Note:      Could compress with ZSTD (50% reduction) in Phase 4+

MMAP FOR RECOVERY:
  Decision:  Use memmap2 for zero-copy reads
  Reason:    O(1) access time, no allocation
  Tradeoff:  Requires unsafe Mmap::map() call
  Impact:    <1 second recovery @ 100K entries
  Note:      Standard mmap safety guarantees documented

CRC64 OVER SHA256:
  Decision:  Use fast polynomial CRC64 instead of SHA256
  Reason:    <20ns computation vs <1000ns SHA256
  Tradeoff:  2^-64 collision vs 2^-256 collision
  Impact:    Acceptable for corruption detection (not cryptography)
  Note:      SHA256 would add <1ms overhead (future option)

ATOMIC OFFSET TRACKING:
  Decision:  AtomicU64 with Relaxed ordering
  Reason:    Lockfree append coordination
  Tradeoff:  Must flush before reading (commit order matters)
  Impact:    <5ns per append
  Note:      File seek handles actual positioning

================================================================================
KNOWN LIMITATIONS & MITIGATIONS
================================================================================

LIMITATION 1: Single-threaded WAL
  Impact:    Cannot append from multiple threads concurrently
  Mitigation: Design assumes single HybridLshCapsule instance
  Workaround: If multi-threaded needed, move lock inside append()
  Timeline:  Phase 2+ (parallel dedup integration)

LIMITATION 2: No Compression
  Impact:    27MB per 100K entries
  Mitigation: Acceptable for 64GB systems (100M entries = 2.7GB)
  Workaround: Enable ZSTD compression (Phase 2)
  Timeline:  Phase 2 (optional optimization)

LIMITATION 3: Sequential File I/O
  Impact:    Blocking fsync() calls
  Mitigation: Acceptable for 100K entries (< 100ms total)
  Workaround: Batch fsync() calls, use async I/O
  Timeline:  Phase 4+ (optimization)

LIMITATION 4: No Replication
  Impact:    Single-node failure → data loss
  Mitigation: Checkpoint-based recovery (Phase 5)
  Workaround: Replicate at application level initially
  Timeline:  Phase 4-5 (enterprise feature)

TECHNICAL SPECIFICATIONS
================================================================================

WAL ENTRY FORMAT:
  Offset   Size   Field        Type          Purpose
  ────────────────────────────────────────────────────────
  0        8      doc_id       u64           Document identifier
  8        256    signature    u16[128]      MinHash signature (Q8.8)
  264      8      crc64        u64           Integrity checksum
  ────────────────────────────────────────────────────────
  Total:   272 bytes

CRC64 POLYNOMIAL:
  ECMA: 0x142F0E1EBA9EA3693

WRENT ORDERING SEMANTICS:
  1. Serialize entry (in-place)
  2. Compute CRC64
  3. AtomicU64::fetch_add(offset) - lockfree coordination
  4. File seek + write - must happen within Mutex lock
  5. Increment entry_count

FILE LAYOUT:
  [Entry 0: 272 bytes]
  [Entry 1: 272 bytes]
  ...
  [Entry N: 272 bytes]

RECOVERY SEMANTICS:
  1. Open WAL file
  2. Verify each entry (CRC64 check)
  3. Skip corrupted entries (record index)
  4. Iterate valid entries
  5. Re-insert into in-memory LSH
