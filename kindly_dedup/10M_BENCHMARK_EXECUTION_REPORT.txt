Memory Layout:
  - Each MinHashSignatureCapsule: ~256 bytes
  - 10M documents: 10,000,000 × 256B = 2.56GB
  - Protected by: 1 global Mutex
  - Access pattern: 10,000+ concurrent workers all trying to acquire same Mutex

Failure Cascade:
  1. extract_candidate_pairs() generates 10K-100K candidate pairs
  2. Verification loop creates 10K-100K tasks (1 per 1000-pair chunk)
  3. All tasks submitted to 16-worker thread pool
  4. Each task attempts to acquire Mutex on 2.56GB vector
  5. Lock contention explodes: 16 workers × 10,000 tasks = 160,000 lock attempts
  6. Task queue grows faster than workers can process
  7. Memory fragmentation from repeated lock/unlock cycles
  8. OOM killer triggers: process killed with SIGKILL (exit 137)

Why It Works at 10K: Only ~10-100 candidate pairs → 1-10 tasks → minimal contention
Why It Fails at 10M: ~100K-1M candidate pairs → 100K-1M tasks → extreme contention

THE FIX (Technical)
================================================================================

Option A: Use Lockfree ConcurrentMapCapsule (RECOMMENDED)
──────────────────────────────────────────────────────

CURRENT (BROKEN):
  signatures: Arc<Mutex<Vec<Option<MinHashSignatureCapsule>>>>

FIXED:
  signatures: Arc<ConcurrentMapCapsuleV2<DocId, MinHashSignatureCapsule>>

Changes Required:
  1. Storage: Vec → ConcurrentMapCapsuleV2
  2. Insertion: `sigs[doc_id] = sig` → `sigs.insert(doc_id, sig)`
  3. Verification: `&sigs[doc1]` → `sigs.get(&doc1)` (returns Option)
  4. Error handling: Unwrap Option properly

Benefits:
  ✓ Zero Mutex (COCA compliant again)
  ✓ True lockfree (atomic operations only)
  ✓ Scales linearly with threads
  ✓ No OOM from contention
