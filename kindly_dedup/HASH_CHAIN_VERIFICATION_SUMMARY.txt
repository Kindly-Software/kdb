ARCHITECTURE
================================================================================

Hash Chain Verification Flow:
────────────────────────────

User runs: cargo run --bin kindly_dedup -- verify

    ↓

TUI calls: verify_hash_chain(lines, verbose)

    ↓

Function calls: verify_audit_trail()  [from atomic_capsule/protection/audit.rs]

    ↓

SecurityAuditLogger::verify_chain():

    1. Read audit trail file
    2. For each line (hex-encoded entry):
       - Decode hex → binary bytes
       - Deserialize fixed fields (61 bytes)
       - Check: prev_hash matches expected?
       - Compute: hash(current entry)
       - Use result as prev_hash for next iteration
    3. Return: Ok(event_count) or Err(cause)

Hash Chain Structure:
─────────────────────

Genesis (entry 0):
  prev_hash = [0u8; 32]

Entry 1:
  prev_hash = blake3(Entry0)  ← Must match!

Entry 2:
  prev_hash = blake3(Entry1)  ← Must match!

...and so on

If any prev_hash doesn't match → Tampering detected!

================================================================================
CRYPTOGRAPHY & SECURITY
================================================================================

Hash Function: BLAKE3
- Cryptographic strength (256-bit output)
- Hardware-accelerated on modern x86 (SSE4.1+)
- Collision resistance: 2^128 (NIST Category 4)
- Designed for high performance + security

Tamper Detection: Hash Chain Links
- Each entry contains blake3(previous_entry)
- Modification of any byte breaks all subsequent hashes
- Genesis hash = [0u8; 32] (all zeros, well-known)

Verification Properties:
- O(n) sequential (must verify all entries)
- Deterministic (same audit trail → same result)
- Collision-resistant (< 2^-128 probability)
- Cannot forge valid chain without source data
